## 2. 用户的核心目标与偏好

- 设计可以在多个国家落地的海外铁路票务平台。
- 子系统划分的主要依据是限制本地定制的改动范围：普通需求应只修改配置、策略或适配器，不应连带修改整个核心。
- 需要区分核心票务、销售交易、席位与选座、产品与价格、开放平台及渠道管理。
- 支持第三方 OTA 和客户自建售票应用；对外 API 不只是网关，还必须有业务实现层。
- 席位布局和人工选座界面允许独立开发；偏好与相邻限制等选座规则允许本地开发。
- 支持动态价格、折扣、上浮、计次票、通勤票，并考虑未来餐饮、零售、酒店、其他交通与多式联运。
- 保留运维中心、国际化及隐私治理能力。
- 架构图只保留一至两张整体图；框名表示模块，框内功能使用“动词＋对象”。
- 用户明确要可运行的模拟系统，而不是卡片桌面推演。

## 3. 当前工作架构：五个业务系统

这是一组逻辑职责，不要求一开始按相同数量独立部署。

| 系统 | 主要归属 |
|---|---|
| 开放平台与渠道管理 | 应用接入、API 管理监控、开放售票接口、OTA 协议适配、渠道权限、资源额度政策、订单映射与通知 |
| 销售交易 | 销售订单、支付退款、授信结算、购买和售后协调、异常恢复 |
| 产品与价格管理 | 产品定义、使用规则、资格规则、版本、动态定价、报价与退改价格策略 |
| 席位配置与选座 | 车厢类型、模板布局、资源属性、人工选座组件、推荐和校验策略 |
| 核心票务 | 铁路基础数据、运行实例与编组、实际资源库存、余票、乘车权益、票证与履约 |

横向支撑：身份权限、租户和国际化配置、隐私治理、运维中心。铁路线路、车站和运营企业主数据仍归核心；公共配置不复制这些主数据。

外部请求主链路：客户自建应用或 OTA → API 网关 → 开放售票及渠道政策 → 销售交易 → 核心及其他领域能力。查询类业务可以由授权应用服务调用相应领域接口，不必把全部只读调用变成订单流程。

## 4. 历史中已经澄清的关键点

### 4.1 订单与“票务预订”

不必再建一套面向旅客的票务预订订单。销售订单由交易系统管理；核心保存与订单明细关联的锁票、占用、权益和票证记录。必要的领域履约记录或外部供应商预订记录并非重复销售订单。

### 4.2 锁票归属

锁票不在理论上必须属于名叫“核心”的系统，而应属于库存的唯一权威服务。当前由于核心拥有席位库且存在多个销售渠道，因此推荐核心统一执行铁路资源的锁定、确认和释放。

铁路核心不接管酒店或零售库存；这些资源由各业务服务或供应商负责。

### 4.3 渠道额度

- API 调用额度：开放平台配置，网关执行。
- 库存类渠道额度、优惠配额：渠道／产品侧定义政策，核心与席位占用协调执行。
- 资金授信：交易账务占用及释放。

三类额度不能混为一谈。

### 4.4 席位模板与实际资源

席位模块发布版本化车厢模板；核心将模板关联到某日期的具体车次编组，再生成实际资源。等级、资源类型和属性分别表达。模板更新不能直接覆盖已售运行实例。

### 4.5 规则与并发

核心不写死各国选座规则。选座引擎根据权威状态快照评估规则；核心校验评估依赖的状态版本并原子执行占用。需要覆盖规则实际读取的数据范围，不能只检查所选座位本身。

初期以车厢版本作保守校验，后续按性能需要细化资源组和区间。人工选座与自动配座共用服务端规则。规则所需敏感信息最小化，不向座位图暴露其他旅客的敏感属性。

### 4.6 定价独立

价格框架加载本地策略，输出标准报价及有效条件；核心提供销售上下文并执行有限配额约束。必须区分“销售数据只是价格参考”和“严格限量的优惠名额”。核心不执行本地价格公式。成交条件保存快照，历史成交不能被新规则无条件重算。

### 4.7 权益与产品

产品定义卖什么，权益实例记录某人实际拥有什么。权益账位于核心的乘车权益管理模块。购买计次票无需当场占座；使用时才按产品规则预约资源并消费权益。扣次时点及取消恢复规则必须显式约定。

### 4.8 多业务扩展

统一销售订单可以包含多个明细，分别关联铁路票证、餐饮履约单、酒店预订等。交易系统协调，领域服务执行。多供应方购买不假定分布式原子成功；需要能力声明、部分失败处理和补偿政策。

## 5. 核心接口范围（设计建议，并非全部已实现）

- 管理类：维护基础数据，创建运行实例，配置编组，生成库存，申请运行变更。
- 查询类：查询车次余票，查询资源状态，获取销售上下文，查询库存操作结果。
- 占用类：申请锁票，确认占用，释放锁票，维护库存配额政策。
- 权益类：签发、查询和校验权益，申请使用，确认使用，取消或恢复使用。
- 履约类：签发和查询票证，记录乘车使用，查询可退改状态，执行退改，查询履约结果。
- 事件类：运行变更、库存变化、权益变化、票证变化及售后结果。

所有命令应具有可信身份、明确版本、幂等请求标识、可查询结果及可区分失败原因。普通售票权限不等于运力或库存管理权限。

## 6. 模拟器实际实现

文件位于本目录上一级，纯 HTML/CSS/JavaScript，无外部包依赖。`engine.js` 是内存中的确定性状态机，逻辑职责以操作和状态账体现，并非真实部署的微服务或 HTTP 后端。

- 一趟列车 A—B—C，区间按半开区间表示。
- 3 个虚构市场配置，14 个预置业务场景。
- 固定／浮动价格、车厢模板、相邻限制、家庭同排选择。
- 库存锁定确认释放、区间复用、渠道及优惠配额。
- 支付、出票、响应丢失、结果核查、到期和补偿退款。
- 计次票签发、次数冻结、确认扣次、取消恢复。
- 余票完整快照事件、旧版本去重、重建。
- 逐步执行、自动播放、手动接口调用、批量验证和 JSON 报告导出。
- 故障开关：跳过版本检查、跳过额度检查、注入重复占用写入缺陷。

交付时 `node verify.cjs` 结果：55/55 通过。其中包含 42 个市场场景组合、3 个故障检出检查、10 个补充边界检查。故障检出测试通过代表成功发现故障，不代表注入故障的业务场景通过。

已做浏览器验证：逐步执行、市场切换、批量验证、故障检出、消息查看、报告下载、手动调用、390 像素移动布局，无运行时错误。执行记录是当次交付证据，不保证今后修改自动正确。

### 当前不覆盖

- 真实数据库锁、跨进程原子性、网络行为、性能和容量。
- 真实支付、API 认证与网关、供应商集成及渠道资金授信。
- 生产级席位编辑器、任意车厢图形布局、全部本地规则。
- 通勤票、复杂权益范围、检票扣次和离线检票。
- 减编重排、已出票退改、餐饮、酒店、多式联运。

模拟器使用同步提交表达原子性要求，并发通过步骤交错表达。它验证设计逻辑，不证明生产实现正确或满足任何标准认证。
