这版模拟器验证什么？
验证模块职责、操作顺序、状态变化、幂等语义、故障恢复及市场配置替换。所有操作在浏览器内存中完成，刷新后数据清空。
明确的模拟假设
  • 固定一趟列车 A—B—C，区间采用 [起点,终点) 表达；相邻关系由每两个资源组成的一排或包厢定义。
  • 核心锁定采用“先完整校验、再一次同步提交”。这只表达原子性要求，不能证明数据库实现具有并发安全性。
  • 规则依赖全车厢版本；版本改变后先重校验。身份组 X / Y 仅用于展示状态依赖，没有采集真实敏感信息。
  • 价格按乘车区间、人数、已售资源比例和策略计算；SIM 是模拟计价单位。等级只展示，尚未设置等级价差。
  • 报价在有效期内保证价格；优惠限额独立由核心执行。锁票成功后保留成交报价，原报价随后过期不撤销已接受的锁票。
  • 权益产品仅模拟记名、30 天有效、A—C 内可用的计次票，确认出票时扣次。尚未模拟通勤票复杂规则与检票扣次。
  • 余票事件携带完整快照，因此可跳过旧版本；如果真实系统采用增量事件，需增加版本缺口检测和补齐。
  • OTA 只模拟订单归属与库存额度；未实现真实网关、授信服务、供应商连接和通信安全。
  • 暂不覆盖减编重排、已出票退改、酒店与餐饮、多式联运。支付后锁票失效的退款是异常补偿场景。
模块协议
怎样使用？
  1. 先逐步运行“正常购票”，观察每一条消息和状态差异。
  2. 再运行并发、超时、权益和事件场景；预期拒绝是通过测试的一部分。
  3. 切换市场 A/B/C，再批量验证同一套核心接口。
  4. 打开“关闭占用版本校验”，运行场景 04；检查器应发现相邻约束被破坏。
  5. 进入自由实验，通过模拟接口发送任意合法请求，导出报告用于架构评审。

 
自由实验 · 手动调用模拟接口
手动调用会进入独立实验模式，保留当前账本但结束预设步骤。请求是 JSON；可根据错误结果修改后重试。
常用路径
quote → validate / recommend → lock → pay → confirm
已有计次权益时：quote（entitlement: true）→ validate → lock（usePass: true）→ confirm
推进时间会执行到期释放；deliver / rebuild 刷新余票投影。错误不会自动伪装为成功。
