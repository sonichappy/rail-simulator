# Rail Lab · 票务架构模拟实验室

## 跨电脑开发

仓库：https://github.com/sonichappy/rail-simulator（私有仓库，需要有访问权限的 GitHub 账号）。

首次在新电脑获取：

```sh
git clone https://github.com/sonichappy/rail-simulator.git
cd rail-simulator
```

继续开发前，先阅读 [项目交接说明](docs/项目交接说明.md) 和相关 [聊天历史](docs/聊天历史原文.md)。随后创建工作分支：

```sh
git switch main
git pull --ff-only
git switch -c feature/your-change
```

验证完成后，提交并推送自己的分支，再通过 Pull Request 合并：

```sh
node verify.cjs
git status
git add <需要提交的文件>
git commit -m "Describe the change"
git push -u origin feature/your-change
```

`verify.cjs` 会更新 `verification-report.json` 的时间戳和结果；提交前检查该文件是否需要随本次改动一起保存。此模拟器没有第三方运行依赖，不需要执行 `npm install`。

## 打开方式

直接用浏览器打开本目录中的 `index.html`。无需安装依赖或连接外网。

如需通过本地地址访问，在本目录运行：

```sh
python3 -m http.server 8765 --bind 127.0.0.1
```

然后访问 `http://127.0.0.1:8765`。关闭终端进程即停止服务。

## 建议的体验顺序

1. 保持市场 A，逐步执行“正常购票”。在状态账本查看席位、订单与资金，在接口消息查看请求、响应和状态差异。
2. 运行“规则校验后状态变化”，理解推荐结果为何不能直接形成占用。
3. 打开“关闭占用版本校验”，重新运行上述场景。系统应报告规则违规；这是故障检出成功，不是正常设计通过。
4. 关闭故障开关，切换市场 B 或 C，执行全部场景，检查公共核心是否仍可承接不同模板和价格策略。
5. 在自由实验区修改 JSON 请求，尝试不同区间、资源、旅客人数、偏好和操作顺序。
6. 导出报告，保存完整执行流水与状态差异，用于架构评审。

## 操作说明

- **执行下一步**：执行一条真实模拟操作，更新相应状态。
- **自动播放**：每 0.8 秒执行一步，可暂停。
- **运行至结束**：执行当前场景剩余步骤并展示验收结果。
- **批量验证**：为每个场景建立独立状态，验证同一市场下的 14 个场景；不改变当前账本。
- **编辑市场配置**：修改布局、资源数量、价格、阈值、额度或权益用量。应用时重置当前实验。
- **场景固定条件**：部分场景固定某一策略或配额，以确保覆盖指定分支；界面明确展示覆盖项，导出报告记录实际配置。
- **自由实验**：保留当前状态及当前实际策略，结束预设步骤；错误消息属于真实模拟结果，没有自动修正。需要完全使用市场配置时，先点击“清空状态开始自由实验”。
- **查看区间**：改变座位图观察范围；不改变已有订单的乘车区间。
- 所有数据都在浏览器内存中。刷新页面会清空；请用导出报告保存证据。

## 第一版范围

### 已实现的可执行模型

- 5 个职责域：开放渠道、交易、产品价格、席位规则、核心库存与权益。
- 版本化的选座判断、原子提交假设、区间重叠、同座分段复用。
- 固定与浮动报价、报价有效期、优惠库存配额、渠道库存上限。
- 锁票、支付、出票、响应丢失、结果核查、超时释放和补偿退款。
- 计次权益签发、用量冻结、确认扣次及取消恢复。
- 带版本的余票完整快照、乱序去重和重建。
- 每步结果断言及资源、额度、权益等不变量检查。
- 可导出的请求、响应、修改前后状态和检查结果。

### 显式简化

- 所有国家／市场是假设数据，身份组 X/Y 不是实际国家政策。
- 只有一趟列车 A—B—C；资源按每两个编号组成一排或包厢。
- 不涉及真实敏感旅客数据、实际收款、网关或网络安全实现。
- 价格单位 SIM 为模拟单位；等级仅展示，本版不计算等级价差。
- 所选区间售出比例按“已售资源 × 覆盖基础区间”统计；锁票不计入此价格指标。
- 权益仅支持 30 天有效的计次票，出票确认时扣次；不包含通勤票和复杂检票政策。
- 单线程同步提交表达事务要求；并发以步骤交错表示，不能验证真实数据库原子性、吞吐量或分布式网络行为。
- 余票事件是完整快照。真实增量事件还需缺口补齐和额外恢复机制。
- 尚未覆盖车厢减编重排、已出票退改、渠道资金授信、酒店、餐饮和多式联运。

## 文件说明

- `index.html`、`styles.css`、`app.js`：交互界面，无第三方依赖。
- `engine.js`：确定性的状态机、场景与不变量；同时供界面及命令行测试调用。
- `verify.cjs`：自动验证脚本。
- `verification-report.json`：交付时的模型验证结果。
- `preview.png`：界面预览。

安装 Node.js 的环境可以在本目录运行：

```sh
node verify.cjs
```

它会重新运行 55 项检查，并更新 `verification-report.json`。其中 3 项检查确认注入缺陷能够被检测到。

## 继续扩展的方法

1. 新增市场：增加配置或策略实现，尽量不修改库存提交逻辑。
2. 新增业务流程：在 `engine.js` 的 scenarios 中添加初始条件、步骤、期望结果及终态判定。
3. 新增核心能力：先定义新的状态与不变量，再添加处理逻辑，并补充失败和重复执行场景。
4. 若扩展策略需要此前不存在的输入或资源语义，应升级契约，不要通过直接改写其他模块账本绕过边界。
